# Configuration and registry formats

English · [繁體中文](../reference.md) · [Back to README](../../README.en.md)

For migration or conversion scripts. A version sampan does not understand is never overwritten; it is reported.

## `~/.config/sampan/config.toml` (`version = 1`)

| Field | Meaning |
|---|---|
| `version` | integer, must be `1` |
| `[restore] recent_days` | non-negative integer, default 7; `restore` pre-checks only sessions active within this many days (after a reboot or a killed tmux server it pre-checks those running at the last save instead) |
| `[ui] start_dir` | path where the directory chooser of `n` (start new work) starts; default `~/Projects` if it exists, else `~` |
| `[ui] detach_key` | string, default `"C-q"`. In a session sampan manages, this key jumps back to sampan: a client attached from outside tmux detaches, and when sampan switched over from inside tmux it switches back to the previous session; in other tmux sessions the key goes to the program as usual. sampan writes the binding into the running tmux server when its screen opens and before attaching (never into `~/.tmux.conf`) and marks its sessions with the `@sampan` session option; if you already bound the key to something else, sampan leaves it and `sampan doctor` says so. `""` binds nothing (and removes a binding sampan wrote). Limits: a session opened outside the `sampan` screen (say `sampan new`, then `tmux attach`) is marked the next time the screen opens or finishes an action; after attaching from outside and switching sessions yourself (`Ctrl-b s`), Ctrl-q switches back to the previous session instead of detaching |
| `[ui] codex_auto_start` | boolean, default `true`. When the `sampan` screen opens and the Codex daemon is not running, run `codex remote-control start` once in the background; `false` never starts it |
| `[mcp] confirm` | boolean, default `true`. The `send`, `send_batch`, `new_session`, `cancel_dispatch`, `folder_move` and `resend` tools of `sampan mcp serve` are approved every time through the agent's own permission prompt (Claude Code's permission prompt, Codex's `approval_mode = "prompt"`); a client not known to ask a person first is refused, never skipped. An agent running `sampan send`, `sampan send-batch`, `sampan new … --message`, `sampan dispatches cancel` or `sampan dispatches resend` from Bash is refused as well. `false` never asks and just acts (still logged in `actions.log`, still cancellable). The read-only `list_sessions` and `dispatch_result` never ask; `inbox_take` and `reply` (receiving mail) are not asked by sampan either (whether Claude Code asks depends on `sampan mcp install --allow-inbox`) |
| `[dispatches] keep_days` | non-negative integer, default `90`. A finished (`done`, `failed`, `cancelled`) dispatch older than this many days loses its bodies: `text`, the reply and every reply part, the text of its deliveries, `extra`; the row, its id and the statistics columns (`text_len`, `reply_len`…) stay, the id is never reused, and `purged` becomes 1. There is no cap on the number of rows any more |
| `[codex] enabled` | boolean, default `true`. With no `agent = "codex"` profile, `[codex]` acts in memory as an implicit Codex profile, converted to `[profiles.<name>]` by the first `sampan profile rename / disable / enable / forget / add --codex`; once any `agent = "codex"` profile exists, all of `[codex]` is ignored; `false` means Codex is off (no Codex profile), and forgetting the last Codex profile writes it |
| `[codex] home` | Codex folder; default `$CODEX_HOME`, else `~/.codex` (only used for the implicit Codex profile) |
| `[marketplaces] <name> = "owner/repo"` | plugin source: GitHub `owner/repo` or a git URL (`https://…`, `ssh://…`, `git@host:path`, e.g. a self-hosted Gitea). Local directories are not supported |
| `[profiles.<name>] config_dir` | required path (`~/` allowed) |
| `[profiles.<name>] default` | exactly one profile is `true`: it only means "which profile is used when none is named" (`sampan new`, the picker's default) and has **nothing to do with setting `CLAUDE_CONFIG_DIR`**. Whether the variable is set follows `config_dir`: the profile whose `config_dir` is `~/.claude` (compared after resolving) starts without it and keeps its login state in `~/.claude.json`; every other profile always gets `CLAUDE_CONFIG_DIR=<its own config_dir>` and its own `.claude.json` (since 0.18.1; before, the `default` one never got the variable, so moving `default = true` to a profile outside `~/.claude` made it run in `~/.claude` without a word) |
| `[profiles.<name>] label` | display text, e.g. an account e-mail |
| `[profiles.<name>] agent` | `"claude"` (default) or `"codex"`; for a Codex profile `config_dir` is its `CODEX_HOME`, and it has no `plugins`. With several Codex profiles, sampan starts Codex with the first enabled one and attributes every running Codex session to it (multi-account is not supported yet) |
| `[profiles.<name>] disabled` | boolean; `true` disables it (hidden, cannot start sessions, skipped by plugins sync); the default profile cannot be disabled |
| `[profiles.<name>] plugins` | list of `plugin@marketplace`; the marketplace must be in `[marketplaces]` |

Overrides: `SAMPAN_CONFIG` (config file, default `~/.config/sampan/config.toml`), `SAMPAN_STATE_DIR` (state folder, default `~/.local/state/sampan/`).

## `registry.json` (`version = 3`, in the state folder)

```json
{
  "version": 3,
  "machine": "…",
  "saved_at": "2026-01-01T09:00:00+00:00",
  "sessions": [
    {"tmux": "work", "agent": "claude", "profile": "alice", "session_id": "…",
     "cwd": "/Users/u/proj", "state": "active", "seen_at": "2026-01-01T09:00:00+00:00",
     "server": "…", "pid": 12345, "id": "…", "alias": "", "model": "sonnet[1m]"}
  ]
}
```

| Field | Meaning |
|---|---|
| `tmux` | tmux session name (unique) |
| `agent` | `"claude"` or `"codex"` |
| `profile` | profile name from config.toml; `""` for codex |
| `session_id` | Claude conversation id, or Codex thread id |
| `cwd` | working directory (absolute path) |
| `state` | `"active"` or `"retired"` |
| `seen_at` | when it was last seen |
| `server` | identity of the tmux server at the last sighting (pid and start time), used to tell "the user closed it" from "waiting to be resumed after a reboot" |
| `pid` | the agent process last seen, an integer or `null` |
| `id` | the session's fixed id (`str(uuid.uuid4())`), unchanged by renames, folder moves and profile switches; the screen shows its first 8 characters. Commands and MCP tools take a name, a full id, or a unique prefix of at least 8 characters (when ambiguous they fail and list the candidates: name plus first 8) |
| `model` | optional (0.20): the `--model` value this Claude session is started with; unset means **no key** (the file is as an older sampan wrote it). A launch argument only, it never writes the profile's `settings.json`; a Codex row cannot have one. An older sampan refuses to read a registry with a `model` in it (as for any key it does not know, and it never overwrites the file); `sampan model <name> --clear` before a downgrade |
| `alias` | the alias: free text, not empty, no control characters, at most 50 characters; `""` is unset (the name stands in). Changing it touches neither tmux nor the id; it applies to Claude's `--name` and the Remote Control name at the next launch |

Version 1 and 2 files are still read (a missing `agent` counts as `claude`, a missing `pid` as `null`; `id` and `alias` are filled in by `sampan migrate`), and 0.15 always writes 3. Sampan 0.14 and earlier refuse a version 3 file instead of overwriting it; to go back to 0.14, downgrade to 0.16 first and run `sampan migrate --revert` there (below). Before a rewrite the previous file is copied to `history/registry-<time>.json` (newest 20 kept) only when a session really changed (`seen_at`, `pid` and `server` do not count).
Times (`saved_at`, `seen_at`, the history file names) are written in UTC (`+00:00`) and converted to local time only for
display; history files left by older versions may be named in local time.

## `folders.json` (`version = 2`, in the state folder)

Session folders, used only by the screen and `sampan folder`; `save`, `restore` and the reboot resume neither read nor write it, and the registry holds no folders. Version 2 is `{"version": 2, "folders": {"<folder id>": {"name": "A", "parent": "<parent folder id or null>", "collapsed": false}}, "sessions": {"<session id>": "<folder id>"}, "pending": {"<name>": "<folder id>"}}`: a folder has its own id and parent, and a session belongs to a folder by its registry `id`, so renaming a session or a folder, or moving it to another level, never loses the membership (only the one entry touched changes); `pending` holds members with no registry row yet (for example a Codex session `sampan new` placed in a folder), waiting by name. Version 1 is `{"version": 1, "folders": {"客戶/甲": {"collapsed": false}}, "sessions": {"<name>": "客戶/甲"}}` (paths as keys, levels separated by `/`, no empty segment, no control character); it is still read, 0.15 always writes 2, and while a member has no `id` yet (before the registry is upgraded) version 1 is still written. A session not listed sits at the top level. Reads and writes take the registry lock; the file is mode 600. A session the registry does not have is not listed, and parents missing from `folders` are added automatically. If the file cannot be read, is not JSON or its `version` is not 1 or 2, the list shows every session flat, every folder operation exits 2 with an explanation, and the bad file is never overwritten.

| Command | Effect |
|---|---|
| `sampan folder list` | Prints the tree: two spaces per level, a folder as `▸ name/` (folded) or `▾ name/`, with its sessions below |
| `sampan folder add <path>` | Creates the folder (and any missing parents) |
| `sampan folder rename <path> <new name> [--merge]` | Changes the last segment only; a same-named folder at that level needs `--merge` to be merged into, otherwise exit 2 |
| `sampan folder rm <path>` | Deletes the folder; its sessions and subfolders move up one level, no session is stopped or forgotten |
| `sampan folder move <name or path>... <destination｜/> [--merge]` | Moves sessions or folders; `/` is the top level; a source that is a path in `folders.json` is a folder, otherwise it must be a session in the registry, else exit 2 |
| `sampan new … --folder <path>` | Only after the session started puts it in the folder (created if missing): exit 0, or exit 1 with the tmux session there (Codex ready but not registered yet); a failed write is only a warning |

`sampan rename`, `sampan forget` and `sampan profile forget` keep `folders.json` in step; a failed sync only adds a line `⚠ 資料夾設定沒同步：…` and does not affect the action.

## `dispatches.db` (`dispatches.json` is only a stub since 0.17; both in the state folder)

Dispatch records: one message sent from a caller session (or the terminal) to a target session. Since 0.17 they live in the sqlite database `dispatches.db` (WAL mode, with its `-wal` and `-shm` files; the file is 600 and the folder 700), no longer in `dispatches.json`; `dispatches.json` is left as a stub `{"version": 3, "dispatches": [], "moved_to": "dispatches.db"}`, which sampan 0.16 and earlier refuse (version 3) instead of overwriting. Between processes the same `dispatches.lock` (fcntl) in that folder is used, and every write happens while holding it; an ordinary open never creates the database (a missing file is an error), only the migration does. The database must not be on a Windows drive (`/mnt/…` under WSL): `sampan doctor` reports an error and sampan refuses to send dispatches there. Tables: `messages` (one row per message, columns below), `deliveries` (each delivery: inbox, paste or direct), `delivery_messages` (which messages share a delivery), `rings` (doorbells), `replies` and `reply_parts` (each reply part), `inboxes` (heartbeats), `meta`. Each `messages` row:

| Field | Meaning |
|---|---|
| `id` | four lowercase hex digits |
| `from_name`, `from_profile`, `from_agent` | the caller (for a person at the terminal, `from_name` is "終端機"; for an agent that is not a sampan session, sending through MCP, it is like "未登記的 session（claude）", and it gets no completion notice) |
| `from_kind` | what the caller is: `terminal` (a person at the terminal), `unregistered` (an agent that is not a sampan session), `session` (a sampan session). Only `session` is ever matched by `from_name` (completion notice, MCP results and cancelling). An old record without it: `terminal` when `from_name` is "終端機", else `session` |
| `to_name`, `to_agent`, `to_profile` | the target session |
| `text` | the full text sent, including the source line; emptied (`NULL`) once the dispatch finished more than `keep_days` days ago |
| `state` | one of `queued`, `sent`, `done`, `failed`, `cancelled` (the only five shown outside; the finer one is `status`) |
| `created`, `sent_at`, `done_at` | UTC ISO times; `sent_at` and `done_at` may be `null` |
| `reply`, `reason` | the reply (the latest part, or `null`); why it failed or was cancelled, or what a queued or waiting one waits for (fixed texts below) |
| `notify`, `notified` | whether to notify the caller when done or failed, and whether that happened |
| `thread_id` | conversation identifier, or `null` |
| `raw` | a direct send (`send --raw`, MCP `raw=true`): `text` is the bare message with no source line; default `false` |
| `extra.restore_profile` | `send --restore --profile X` (MCP `profile`, 0.19): the profile the registry row is changed to before the reattach; without this key the registered one is used |
| `extra.restore`, `extra.restore_phase`, `extra.restore_at` | `send --restore` (MCP `restore=true`, 0.18): `restore` is `true` when the sender asked for a stopped target to be reattached first; `restore_phase` (`launching`, `starting`, `rc`, `ready`) and `restore_at` (UTC) are the reattach progress that such dispatches for one target share; `resend` clears the progress and keeps `restore` |
| `batch` | batch id (`b` plus 4 lowercase hex), `null` when not sent as a batch; the dispatches of one batch share it |
| `to_id`, `from_id` | the registry `id` of the target and of the caller; after a rename the other side is still found by it, so a rename mid-flight loses neither the reply nor the notice. `""` in old records (found by name instead) |
| `machine` | the id of the machine the dispatch was made on |
| `batch_skipped` | meaningful on the first item of a batch only: how many sessions the batch skipped (for the completion notice); default `0` |
| `status` | the finer state, below; an old record without it gets it from `state` (`sent` counts as `pasted`, `done` as `replied`) |
| `in_reply_to`, `thread` | reserved fields (which message this answers, which thread it belongs to); nothing uses them in 0.17.0 |
| `text_len`, `reply_len`, `purged` | the lengths of the text and reply (kept after the bodies are purged), and whether the bodies were purged (`0` / `1`) |
| `extra` | keys this sampan does not know (JSON), kept as they were; cleared with the bodies |
| `startup` | the startup message of `sampan new --message` (the new session may not be registered yet); an old record without it counts as `false` |

**The finer `status`** (the `state` shown outside does not change; `dispatch_result` and `sampan dispatches show` give `status` as well, and `search --state` knows both):

| `status` | Meaning | `state` outside |
|---|---|---|
| `queued` | waiting in line | `queued` |
| `rung` | doorbell rung, waiting for the target to take its mail | `queued` |
| `taken` | taken, the target is still working | `sent` |
| `partial` | has a reply part, the target is still working | `sent` |
| `pasted` | full text pasted, waiting for a reply | `sent` |
| `replied` | the turn ended with a reply | `done` |
| `unanswered` | taken, but the turn ended with no reply (that turn is not in the transcript: `/clear`, another conversation) | `failed` |
| `failed` | could not be sent, the target stopped, was interrupted… | `failed` |
| `cancelled` | cancelled by the sender | `cancelled` |

When the target calls `reply` after `unanswered` (its delivery not archived), a part is added, the status becomes `replied` and the sender is notified. Messages taken but not answered (`taken`, `partial`, `unanswered`) are listed in the result of the target's next `inbox_take`, also after a `/clear` or a compaction.

**`how` of each reply part**: `tool` (a tool reply: the target used `reply`), `marker` (split by markers: a pasted delivery is cut at a line-start `〔回覆 <id>〕`), `whole` (the whole reply), `fill` (filled in: the turn ended with no reply for it, so the last text of that turn is used). The `reply` column is the latest part; every part is in `replies` of `dispatch_result` and in `sampan dispatches show`.

**Fixed `reason` texts** (the same set in `dispatch_result`, `dispatches show` and `actions.log`):

| `reason` | When |
|---|---|
| 對方正在忙 | queued, the target is busy (「對方在等使用者回應」 when it waits for the user) |
| 已按門鈴，等對方取信（<code>，<HH:MM>） | `rung`: the doorbell line was typed, waiting for `inbox_take` |
| 對方沒有可用的 sampan MCP，改用貼全文 | no valid heartbeat, pasted this time |
| 門鈴沒人應，改用貼全文 | the target is idle and the turn after the doorbell ended without a take (or the doorbell is not in its transcript 15 seconds after it rang, nor left in its box); pasted instead. An idle or stopped target holds a doorbell 10 minutes at most |
| 對方停在權限提示（可能是 inbox_take 沒允許） | rung, and the target sits at a permission prompt |
| 已取走，對方還在做 | `taken` |
| 已有回覆段落，對方還在做 | `partial` |
| 已取走，這一輪結束卻沒有回覆 | `unanswered` |
| 寄件者已取消 | a message that had already reached the target was cancelled |
| 排在前面的派工還沒送完 | an earlier delivery to the same target has not ended; a direct send waits for those before it, and the ones after it wait for it (not in the 0.17 spec's fixed list: added during implementation) |

The older reasons (「對方 session 已停止」, 「對方沒回這則就換了下一則」, 「找不到回覆」…) are unchanged.

**One active delivery per target.** Messages queued for one target (from any sender) are delivered together in time order: a pasted delivery starts with one header line, `〔sampan 轉送｜<N> 則，依時間順序；前後衝突時以後面的為準｜每則請用〔回覆 <派工id>〕開頭分段回覆，sampan 會帶回〕`, and the reply is split at line-start `〔回覆 <id>〕` markers into one part per message; a message whose marker is missing gets the whole reply. A direct send (`raw`) keeps its place and is never merged. Whoever advances any one message moves that target's whole line. Codex targets always get the full text pasted in 0.17.0 (no doorbell), and a second message to a Codex target now waits until the first is answered (it used to go straight into `codex queue`).

**The doorbell and the inbox (Claude targets).** When the target's sampan MCP has a valid heartbeat, sampan does not paste the text; it types one doorbell line into the target's box: `〔sampan 門鈴 <code>〕你有 <N> 則新訊息（來自 <name> <count>、…）。請呼叫 mcp__sampan__inbox_take 一次取完、全部看完再動手；每則做完用 mcp__sampan__reply 回一次（那是最終回覆，不要用來報進度）。工具沒載入時先用 ToolSearch 找 sampan。`. The agent calls `inbox_take` (takes everything at once, with a receipt id, in time order) and answers each message with `reply` when done; when the turn ends with messages still unanswered, the last text of that turn fills them in (`fill`). A turn end needs two idle looks in a row. Heartbeat: every `sampan mcp serve` writes one at most every 30 seconds; it is valid for 2 minutes, with the process alive and its start time matching, the conversation id equal to the one the registry sees now, and version ≥ 0.17. A doorbell counts as unanswered, and the messages are pasted instead, as soon as the target is idle and the turn after it ended without a take, or when it is not in the target's transcript 15 seconds after it rang (nor left in the box); 10 minutes is only a cap: an idle or stopped target holds a doorbell 10 minutes at most. Limitation: calling `inbox_take` from a subagent writes the receipt into the subagent's transcript, so sampan never sees the end of the main conversation's turn and those messages end as 「已取走，這一輪結束卻沒有回覆」.

**`resend`** (`sampan dispatches resend <id>`, MCP `resend`): only for failed, cancelled or done dispatches. The id, the old reply parts and the original `created` are kept; the old deliveries are archived, and a late reply to an old delivery is history only and does not count as this run's reply; the 30-minute queue limit counts from the resend.

A dispatch made by `sampan new --message` starts as `sent` (`sent_at` is when the session was opened; `text` and `outbox/<id>.txt` do not end with a newline, because `$(cat …)` drops trailing newlines and the reply would not match); the conversation id is filled in by later advances from the status rows. While the new session is not recognised yet it is not failed, and `reason` says 「對方 session 還在啟動」: a Codex without a conversation yet (unregistered) is waited for as long as that Codex runs; a tmux session whose agent is not seen yet (a registered Claude shown as 「已停止」, or no agent) for at most 120 seconds; a folder-trust or other startup prompt for as long as it is shown.

How the state moves: `queued` → `sent` (delivered, `sent_at`) → `done` (`reply` is the reply to this message) or `failed` (`reason` says why); `cancelled` comes from `queued` (never sent, `reason` 「已取消」; a rung one counts too, and a later take no longer hands it over) or from `sent` (taken, with a reply part, or pasted: stop waiting for the reply; the message is already with the target, `reason` 「寄件者已取消」, no notice; records written by 0.16 say 「不再等回覆」). A reply that arrives after the cancel is kept as history only and changes no state. `done_at` is when it finished. Every step is taken inside the lock (read the latest, decide, write), so one dispatch is never delivered twice. Before any key is pressed or `codex queue` runs, the record is written as `sent` (`reason` 「送出中」): if sampan is killed in the middle, the dispatch is never sent again (it later fails as 「找不到回覆」), so it is delivered at most once; it goes back to `queued` only when nothing was sent for sure (text in the target's box, an unreadable screen, a failed tmux load…). If Enter fails after the paste (the text is already in the target's box) or `codex queue` times out (Codex may have taken it), it becomes `failed` (「可能已送出，請確認」) and is never sent again (the same for the completion notice: it counts as notified, with the `reason` saying so). A target pane in tmux copy mode gets nothing; the dispatch stays queued.

How a `sent` one ends: when the target is idle and its transcript has an answer after this message → `done`; another message was typed after this one with no answer in between → 「對方沒回這則就換了下一則」; a Codex turn that completed without reply text, or a Claude target idle twice in a row without reply text → 「對方這輪結束了，但沒有回覆文字」; idle twice in a row without the message → 「找不到回覆」 (seeing the target busy in between starts over).

How a direct send (`raw`) ends: after the paste and Enter, as soon as the target's Claude is idle again and the command shows in its transcript (a user record equal to the text or holding `<command-name>/X</command-name>`, or a `system` / `local_command` record) → `done`; the reply is the answer text after it, or 「指令已執行（沒有文字回覆）」 when there is none. If the conversation id changed (`/clear`) → `done` with the reply 「對方換成新對話（first 8 of the id）」. If after the send the screen sits at a menu or prompt (two looks in a row) → `failed` 「指令打開了選單，請自己到那個 session 處理」, and sampan presses no key. A busy target is never judged to be at a menu. Content limits: one line, starting with `/`, at most 500 characters, no control characters, Claude only (to Codex it is refused: 「直接送目前只支援 Claude」).

Batches: every item of a batch is its own dispatch; only sessions that are `running` and idle are sent to, the others are not queued and count as `skipped` (with a reason). When every item has ended (`done`, `failed`, `cancelled`) **one** notice goes out, `〔sampan：批次 <id> 完成：N 完成、M 失敗、K 跳過，用 dispatch_result 看〕`, with no per-item notices; if one item fails or is cancelled the batch still ends and notifies. `sampan dispatches show` does not take a batch id.

Exit codes of `sampan send`: 0 sent or queued (`--wait`: answered), 1 failed, 2 refused or the file cannot be read, 124 `--wait` timed out (the dispatch stays), 130 Ctrl-C (the dispatch stays). `sampan dispatches show <id> [--wait seconds]`: advances it once (or every 2 seconds until it is finished, for at most that long) and prints the state (with the finer status), from whom to whom, the reason, the whole reply, every reply part and every delivery; exit 0 answered or still going (without `--wait`), 1 failed or cancelled, 2 no such dispatch or the file cannot be read, 124 `--wait` timed out, 130 Ctrl-C. The completion or failure notice (`notify`) goes to the caller's session through `outbox/<id>-notice.txt`: `〔sampan：<target> 已回覆派工 <id>，用 sampan 工具 dispatch_result 看內容〕` when done, `〔sampan：給 <target> 的派工 <id> 失敗：<reason>〕` when failed.

The other ways to look at dispatches (all read-only): `sampan dispatches [--all] [--by-target]` (by default only the queued and waiting ones; `--by-target` groups by target with the queued and waiting counts and the heartbeat), `sampan dispatches search [keyword] [--from name] [--to name] [--since date] [--until date] [--state state] [--limit n]` (the keyword is matched literally against `text` and `reply`, so a purged message is only found by its other columns; `--from` and `--to` repeat and take a name, alias, id or id prefix; dates are `YYYY-MM-DD` in Taipei time and `--until` includes that day; `--state` takes one of the five `state` values or a finer `status`; newest first, 50 by default, `--limit 0` for all; one line per message: id, time, from, to, state, first 60 characters) and `sampan dispatches inbox <session>` (one session's inbox: how many queued, rung and taken without a reply, its heartbeat, its last doorbell, and its 20 newest messages). `sampan dispatches resend <id>` resends (above); like `cancel`, it is refused when an agent runs it from Bash while `[mcp] confirm` is on.

`sampan send-batch NAME… -m message [--raw] [--restore [--profile PROFILE]] [--wait] [--timeout seconds]` and `sampan send-batch --folder path -m message` (subfolders included; names or `--folder`, not both): exit codes as for `sampan send`; `--wait` waits for the whole batch and prints each reply; skipped ones are listed (the exit code is not affected).

The caller of `sampan send` / `sampan new --message` is also found from the parent processes (as for MCP): run by an agent through its shell tool, it is recorded as that sampan session (or 「未登記的 session」), and sending to itself is refused; only with no claude / codex process above it is it 「終端機」. These two commands send no notice; read the reply with `sampan dispatches show`.

A file that cannot be read is never overwritten; when the database cannot be opened, a command that needs it fails (exit 2) instead of creating an empty one. A finished dispatch older than `[dispatches] keep_days` (default 90) days loses its bodies (see that field), at most once an hour; the 7-day and 200-row limits are gone. `outbox/<id>.txt` holds the exact text to deliver (mode 600) and is deleted with the bodies.

## The tools of `sampan mcp serve`

A stdio MCP server (one JSON-RPC 2.0 message per line; protocol version `2025-06-18`, or `2025-03-26` when the client asks for it). Claude Code or Codex starts it; the caller is found from the server's parent processes: the tmux pane of the nearest claude / codex process, then the registry row of that tmux session with the same agent. When that does not match, the caller is an "unregistered session" (the source line and the dispatch record say for example 「未登記的 session（claude）」, or 「未登記的 session」 when no agent process is above the server or ps cannot be read at start; an MCP caller is never 「終端機」): the tools still work, it only gets no completion notice. The caller is looked up again before every tool that acts or reads a dispatch (a Codex session is registered only once its conversation exists, a session may be adopted or renamed); only a lookup that cannot read tmux, ps or the registry keeps the identity already known; a definite miss (no row, another agent) makes the caller unregistered. `dispatch_result` and `cancel_dispatch` only accept this caller's own dispatches (created by this server, or with `from_kind` `session` and the caller's session as `from_name`); any other id gets 「沒有派工 <id>（或不是這個 session 發出的）」. Tool results are JSON text; a refusal (unknown target, a client that does not ask a person first, Codex tools not set to ask every time) is a result with `isError: true`.

| Tool | Arguments | Returns | Approval |
|---|---|---|---|
| `list_sessions` | none | `machine` (`id`, `name`: this machine); `sessions`: each with `name`, `id` (the full id; other tools take a name or an id), `machine` (this machine's id), `alias` (`""` when unset), `model` (`""` when unset), `agent`, `profile`, `cwd`, `folder` (its folder, `""` is the top level; all `""` when `folders.json` cannot be read, with a `warning` saying so), `state` (`running`, `stopped`, `retired`…; the older combined display value: a retired session is always `retired`, read `live` to know whether it runs), `registry` (what the registry says: `active`, `retired`, `""` when not registered; 0.27), `live` (whether it really runs: `running`, `stopped`, `unknown` when tmux cannot be read; 0.27), `activity` (`idle`, `busy`…), `last` (UTC ISO or `null`); plus `warning` when tmux cannot be read | never asks |
| `send` | `session` (name or id), `message`, `raw` (default `false`; direct send: one line, starting with `/`, at most 500 characters, Claude only), `wait` (default `false`) | `dispatch`, `state`, `reply` once done, `reason` while not sent yet. `wait` waits at most 60 seconds; a dispatch not finished by then stays, and a notice goes to the caller's session when it is done or fails | asks |
| `new_session` | `name`, `target` (`claude:<profile>`, `<profile>` or `codex`), `cwd`, `message`, `folder` (optional, as `sampan new --folder`; created when missing), `model` (optional, as `sampan new --model`; Claude only) | `dispatch` (the startup-message dispatch, as with `sampan new --message`). A new directory's trust prompt: with `confirm = true` and Claude Code as the caller (its permission prompt shows the whole arguments; not verified for Codex, which gets no automatic trust) you saw the `cwd` in the permission prompt, so sampan trusts for you only the prompt that shows exactly that `cwd`; any other prompt (another directory, an update, an unrecognised menu), and every prompt with `confirm = false`, gets no key: the result is `isError` saying which prompt it stopped at and `tmux attach -t <name>` to handle it, and the startup message starts once it is handled (the dispatch can still be read with `dispatch_result`). A Claude that does not come up in time (for example at a login or theme screen) is an `isError` too; a directory sampan trusted for you is named in the message | asks |
| `send_batch` | `sessions` (a list of names, no duplicates), `message`, `raw` (default `false`), `wait` (default `false`, up to 60 seconds) | `batch` (the batch id), `items` (each `session`, `dispatch`, `state`, `reply` / `reason`), `skipped` (a **list**, each `session`, `reason`). Sends only to sessions that are running and idle, the others are not queued; one notice when the whole batch is done | asks (once) |
| `dispatch_result` | `id` (a dispatch id, or the batch id from `send_batch`), `wait` (0–60 seconds, default 0) | `dispatch`, `state`, `label`, `to`, `reply` (the latest part), `reason`, plus the 0.17 `status`, `status_label`, `replies` (each: `id`, `how`, `how_label`, `at`, `latest`, `late`, `text` up to 2,000 characters), `deliveries` (each delivery), `last_ring` (the last doorbell) and `merged_with` (the other dispatches delivered with it); the old fields are unchanged. Given a batch id it returns the whole batch: `batch`, `items`, and `skipped` is a **number** (how many were skipped) | never asks |
| `cancel_dispatch` | `id` (a dispatch id; a batch id is refused, cancel the items one by one) | `dispatch`, `state`; a queued one is cancelled (a rung one too), a sent one is no longer waited for (plus `reason` 「寄件者已取消」) | asks |
| `resend` | `dispatch_id` (a dispatch id; a batch id is refused) | `dispatch`, `state`, `reply` once done, else `reason`. Only failed, cancelled or done dispatches | asks |
| `inbox_take` | none | plain text: takes every new message sent to you at once (in time order, with a receipt id, the sender and the time) and lists the ones taken earlier that are still unanswered; nothing new is handed over while the previous delivery has not ended | never asks |
| `reply` | `dispatch_id` (as `inbox_take` lists), `text` (up to 100,000 characters), `receipt` (optional, the receipt id) | a plain-text confirmation. It is the final reply to the sender: answer when done, once per message, no progress reports; one arriving after a cancel or resend is kept as history only | never asks |
| `folder_move` | `sessions` (a list of names), `folder` (a path, `/` is the top level; created when missing) | `moved`, `folder`. Like `sampan folder move` it only changes the grouping on the screen; one unknown name, a bad folder name or a broken `folders.json` and nothing changes | asks |

Approval is done by the agent's own permission prompt: with `confirm = true` the tools that act (`send`, `send_batch`, `new_session`, `cancel_dispatch`, `folder_move`, `resend`) carry `_meta["anthropic/requiresUserInteraction"] = true` in `tools/list`, so Claude Code shows its own permission prompt on every call (in the terminal every time, also in auto and bypass modes, with no "don't ask again"; in Remote Control it is expected to show the full permission prompt with no one-tap approve, which is not yet verified on a phone). The prompt shows the tool name and its whole arguments; to decline say No, and to change the message ask the agent to change it and send again (sampan has no form of its own any more, and no "edit the message" field). A name, target or directory with a newline or control character is refused before anything is sent. `new_session` runs the same checks as `sampan new` (name, disabled profile, Codex turned off, tmux session exists, missing directory). Approving a dispatch approves its completion or failure notice; there is no second question. Once `dispatch_result` has shown a done or failed result, no notice is sent. While the server runs it advances this caller's dispatches every 3 seconds (the session states are read once per round; a dispatch of which only the completion notice is still owed, to a sender that is not running, is tried every 30 seconds instead); every program it runs gets `/dev/null` as stdin, so none reads the JSON-RPC input.

The source line says who the dispatch comes from, its id, and tells the receiver to answer in text (`〔sampan 轉送｜來自 <who>｜派工 <id>｜直接回覆文字即可，sampan 會帶回〕`: "just reply in text, sampan brings it back"); completion and failure notices are unchanged.

### Installing, and how approval works

`sampan mcp install` runs `claude mcp add --scope user sampan -- <sampan path> mcp serve` for every enabled Claude profile (with that profile's `CLAUDE_CONFIG_DIR`), and `codex mcp add sampan -- <sampan path> mcp serve` when Codex is enabled (with `CODEX_HOME` when the Codex home is not `~/.codex`); where it is already installed it is skipped. Whether a Claude profile has it is read from its `.claude.json` (`~/.claude.json` for the default profile), `mcpServers.sampan`, without running `claude` just to look (a run can renew the login); only when that file cannot be read or has another shape does it ask `claude mcp get`. `sampan mcp uninstall` does the matching `remove`. Both take `--dry-run`, and `--profile <name>` (repeatable, Codex by its profile name) to handle only those profiles; an unknown name does nothing and exits 2. Each result line is logged in `actions.log` (label `mcp`). Restart the profile's sessions to see the tools. `sampan doctor` shows one line with where it is installed (nothing when it is installed nowhere).

**`--allow-inbox`** (`install` only): adds `mcp__sampan__inbox_take` and `mcp__sampan__reply` to `permissions.allow` in each Claude profile's `settings.json`, so an agent that gets a doorbell takes and answers its mail without Claude Code showing a permission prompt (without it the doorbell can sit at a permission prompt, and the dispatch says 「對方停在權限提示（可能是 inbox_take 沒允許）」). With the flag it does not ask; without it, on a terminal it asks once, 「讓 agent 取信和回覆不用每次按允許？(y/N)」; with no terminal and no flag it adds nothing. Before touching the file it backs it up as `settings.json.bak-sampan-<time>`, appends only the missing two entries to `allow`, keeps every other key and entry and their order, and reads and writes UTF-8; a `permissions.allow` it does not recognise is left alone, with a message. `uninstall` always removes the two entries (even when `claude mcp remove` fails). `sampan doctor` says in one info line per profile with the sampan MCP whether taking and answering mail needs an approval.

How `[mcp] confirm = true` works (fail closed):

- **Claude Code**: the tools carry `anthropic/requiresUserInteraction`, so every call is asked, even in auto and bypass modes.
- **Codex**: `sampan mcp install` writes `approval_mode = "prompt"` under `[mcp_servers.sampan.tools.<tool>]` in Codex's `config.toml` for `send`, `send_batch`, `new_session`, `cancel_dispatch`, `folder_move` and `resend`; `inbox_take` and `reply` are written as `approve` while `confirm` is on (receiving and answering mail asks nothing). `send_batch` is new in 0.14 and `resend` in 0.17: **run `sampan mcp install` again for Codex**; until then Codex refuses the new tool (`resend` answers 「Codex 的 sampan 工具沒設成每次詢問（<path>）：跑 sampan mcp install」, the other tools keep working) and `sampan doctor` says 「Codex 的 sampan 工具表要更新」; with `confirm = false`, or on `uninstall`, it removes only the tables set to `prompt` (user-set `approve` tables are left). Before touching the file it backs it up as `config.toml.bak-sampan-<YYYYmmdd-HHMMSS>`; only sampan's tables change, every other byte (CRLF and comments included) is kept, and the file is read and written as UTF-8. A result that is not valid TOML is not written. If the user picks "always allow" in a Codex prompt, Codex rewrites it to `approve`: `sampan doctor` reports it, and `sampan mcp install` puts `prompt` back.
- **Only clients known to ask a person**: with `confirm = true` these tools run only for `claude-code` and `codex-mcp-client`; any other client gets 「這個 client 不會先問使用者；要用請在 config 設 [mcp] confirm = false」. The direct parent process of `sampan mcp serve` must also be `claude` or `codex` (checked once at start; a failed lookup counts as no): a shell piping JSON-RPC into `sampan mcp serve` and claiming to be `claude-code` is refused, but the name check can be faked (see the limits below). `codex exec` with approval policy `never` cannot ask anyone, so Codex refuses these tools (verified) rather than running them. For Codex the tool must also be `approval_mode = "prompt"` in both the `CODEX_HOME` Codex runs with (else `~/.codex`) and sampan's configured Codex home, else 「Codex 的 sampan 工具沒設成每次詢問（<path>）：跑 sampan mcp install」.
- **`sampan doctor`** checks it: 「Codex 的 sampan 工具沒設成每次詢問（[mcp] confirm = true）：跑 sampan mcp install 補上」, 「…還設著每次詢問（[mcp] confirm = false）：跑 sampan mcp install 拿掉」, 「Codex config.toml 讀不了：…」.
- **Commands run by an agent from Bash**: with `confirm = true`, `sampan send`, `sampan send-batch`, `sampan new … --message`, `sampan dispatches cancel` and `sampan dispatches resend` run by an agent (not a person at the terminal) are refused (exit 2); set `[mcp] confirm = false` to let agents use the commands directly.
- **After changing `[mcp] confirm`**: Claude reads it when its MCP server restarts (a new session, or `/mcp` reconnect); Codex needs `sampan mcp install` again.

Limits:
- Whether a Codex started with `--dangerously-bypass-approvals-and-sandbox` still asks is not documented officially, and was not tested: treat it as unverified.
- This does not stop an agent that types into tmux panes itself (`tmux send-keys`). Claude Code's sandbox can, but sampan does not set it up.
- The parent check looks only at the process name: it stops an agent that simply pipes JSON-RPC into `sampan mcp serve`, but a name can be faked (for example `exec -a claude`, or a link named claude), so, like `tmux send-keys` or editing `[mcp] confirm`, it does not stop an agent that deliberately works around sampan.

## `sampan restart <name…>`

Restarts the named sessions; each result is logged in `actions.log` (label `重開`). Classification: running in the registry with `agent_status` `idle`, and not in the pane sampan itself runs in, then `sampan stop` (90 second timeout) and a background reattach; stopped, then only reattached; busy (`busy`, `working` or `waiting`, reason 「忙」), any other status that is not idle (reason for example 「沒有閒著（unknown）」), retired, state unknown, any other state or not found, then skipped, with a final line "略過：name（reason）…". The reattach is a `restore` without confirmation that does not take you in by itself; an agent that stops at a startup menu (trust this directory and so on) is waited for and its question handed to you, as with `R` (by number in a terminal); in the sampan screen, choosing "go in and do it yourself" takes you into that session. Exit 1 when there is nothing to restart or reattach; otherwise the worst exit code of stop and restore.


## `sampan rc <name…>` (0.21)

```
sampan rc <name…> | --all | --profile <p>   [--dry-run] [--yes]
```

Corrects only the Remote Control name of **running** Claude sessions, without restarting them or reloading their context (since 0.23 a session whose Remote Control is connected only gets `/rename`; see "standard steps after launch and the RC reset" below). Names resolve as for `restart` (name, id, unique id prefix); `--all` (every registered session) and `--profile <p>` (those registered on p) combine with names as a union, and `--all` with `--profile` as the intersection. Classification: running, `agent_status` `idle`, Claude, profile with `remoteControlAtStartup` → corrected; busy (`busy`, `working` or `waiting`, reason 「忙」), any other status that is not idle, stopped (「已停止；下次接回會自動套用」), retired, state unknown, Codex (「Codex 沒有 Remote Control」), a profile without Remote Control, the pane sampan itself runs in, or not found → skipped, listed by reason at the end. The correction is `steps.rc_rename`: the same as the RC reset after a reattach (only text plus Enter, Up, Enter and Escape; Enter only with the cursor verified on `Disconnect this session`; an unrecognised screen gets Escape and a reason), except that it does not wait for "/remote-control is active" on the screen (a session that has run for a while has no such line) and starts from the empty input box instead; with text in the box, or no box, it presses nothing. A session whose Remote Control is not connected connects at `/remote-control` instead of opening the menu; sampan waits for the menu to follow and types the command once more only if it does not. One session at a time, 0.5 seconds apart; each one's state is read again right before its turn (busy by then: skipped). `--all` / `--profile` print the plan and ask `確定？(y/N)` in a terminal, and need `--yes` without one; `--dry-run` prints the whole plan and presses nothing. Every message goes into `actions.log` (label `RC 校正`); on a failure the last 40 lines of the screen (at most 160 characters each) are written there too, in that local file only, never printed. Exit 0 when nothing failed (skips are not failures), 1 when any failed or Ctrl-C interrupted it, 2 for a name not found or a bad argument. An agent may run it for other sessions, never for its own pane (skipped); `[mcp] confirm` does not apply, and there is no MCP tool. Each correction adds a new entry to the phone app's Remote Control list (the old one goes offline).
## Standard steps after a launch, and the RC reset

After reattach (`restore` / `R` / Enter), restart (`restart` / `S`), `switch`, `move` and `adopt`, once Claude is back at its prompt and when the profile has Remote Control on (`remoteControlAtStartup`), sampan does one RC reset: it waits for the session file's `bridgeSessionId` to have a value (Remote Control connected; with no readable file or no such field it falls back to waiting for `/remote-control is active` on the screen) and, with the input box empty, types `/rename <alias, or the name when unset>`; it is done when the session file's `name` is the alias (for the same name: `nameSince` or `updatedAt` moved) with `bridgeSessionId` still there, or the screen says `Session renamed to: <alias>`, and after 10 seconds without either it prints `改名沒確認`. That means no disconnect, no menu and no new entry in the phone's list. Without a `bridgeSessionId` it falls back to the old way: it types `/remote-control`, presses Enter only when the menu's cursor is verified on `Disconnect this session`, then types `/remote-control <alias, or the name when unset>`, which adds a new entry to the phone app's RC list while the old one goes offline. It does this on every launch without judging whether the name is already right. The only keys sampan presses are text plus Enter, Up, Enter and Escape; if the screen is not what it expects it presses Escape and prints `RC 校正沒做：<reason>`, and the operation and its other steps and exit code are unaffected. `new` does not do it (a new conversation gets the right name directly), and neither can the in-place reattach inside sampan's own pane (sampan exits first). A single Enter on a stopped row in the screen waits for the reattach and the reset before taking you in: meanwhile it prints `… <name>：RC 校正中（最多約 20 秒）`, and keys pressed during the wait are dropped (they do not start a second reattach); when the reset is not done, the message adds that `S` (or `sampan restart <name>`) will do it again. By hand it is `/remote-control` → `Disconnect this session` → `/remote-control <name>`. To fix an existing session's name, set the alias with `sampan alias`, then `sampan restart <name>` (an agent may run it from its shell for other sessions; busy ones and its own pane are skipped).

## `sampan alias <name> <alias>`, `sampan alias <name> --clear`

Sets or clears the alias (rules under `alias` in `registry.json`); `L` on the screen. Refused (exit 2) when an agent runs it from Bash while `[mcp] confirm` is on.

## `sampan migrate [--dry-run | --revert]`

Upgrades the data to the current format. The 0.15 step: `registry.json` to 3 (filling in `id`) and `folders.json` to 2. The 0.17 step: `dispatches.json` (version 1 or 2) moves into `dispatches.db`, and `dispatches.json` becomes the stub (above). You normally never run it: the first 0.17 command of any kind does it automatically. The 0.15 step copies the state files that exist into `backup-0.15-<time>/` in the state folder (never deleted; a retry after a failed run with identical content reuses the same backup), writes the new format, re-reads and compares session count, names, conversation ids and folder membership, and on any difference restores from the backup and reports. The 0.17 step runs under `dispatches.lock`, writes a journal it can resume from (`migrate-0.17.json`), copies the original file into `backup-0.17-<time>/` (never deleted), builds the database and compares it message by message; if a 0.16 changed `dispatches.json` meanwhile it starts again (at most 3 times), and on any difference it throws the database away, leaves the original untouched and reports. Both steps can be run again and do nothing when the data is already new. A broken `folders.json` is kept as it is with a warning, and the registry is still upgraded.

- `--dry-run`: tries it on a copy and prints the before/after difference and how many ids would be made; the real files are untouched (read-only).
- `--revert`: writes the dispatches back into a `dispatches.json` that 0.16 reads (version 2; only the ones whose text is still kept, so purged ones are not in it; one still in a group paste or taken through the inbox and being worked on is written as `failed` with the reason 「降版時還在處理，請重送」, since 0.16 could never find its reply), renames the database to `dispatches.db.reverted-<time>` and keeps it, and leaves a mark `migrate-0.17.reverted`; the registry and folders keep the 0.15 format, which 0.16 reads. **Run it with 0.17 before downgrading to 0.16.** After a revert the 0.17 commands that touch dispatches (`send`, `send-batch`, `new --message`, `dispatches`, `mcp serve`) refuse with 「已降回 0.16 格式；要再升級請跑 sampan migrate」 (exit 2) and the other commands work; to upgrade again run `sampan migrate` (it removes the mark, then moves the data again). The next time 0.16 writes dispatches it applies its own rules and drops finished ones older than 7 days (200 kept at most). Going back to 0.14 is no longer something the 0.17 `--revert` does: downgrade to 0.16 first, run `sampan migrate --revert` there, then downgrade.
- `sampan doctor` shows the data versions of the registry, folders and dispatches and the last backup; it reports an error when the dispatch database cannot be read, and a warning when the registry cannot.
- When the 0.17 migration fails (exit 2) only the commands that touch dispatches are stopped; the others work. `dispatches.json` is untouched.
- After upgrading, a session still running an older `sampan mcp serve` cannot read the new registry and the dispatch database, and its sampan tools fail until that session is restarted; restart every session once (`S` on the screen, or `sampan restart`). After `sampan update`, after `U` on the screen, and at the first command that may print after the 0.16 → 0.17 migration, a notice is printed once: which sessions need a restart, and that the Codex tools table needs `sampan mcp install` again. Until the restart those sessions fail to send, and senders to them paste the full text.

## `machine.toml` and `sampan machine`

`machine.toml` sits in the same folder as `config.toml`: `id` (made on creation) and `name` (editable; default the hostname without `.local`). `sampan machine` prints both; `sampan machine --name X` renames the machine (the id does not change; refused for an agent while `[mcp] confirm` is on). The id is written into the registry and the dispatch records, and MCP `list_sessions` returns it as `machine`. A cross-machine reference is written `<machine id>:<session id>`; only the format is defined so far.

## `sampan switch` (several at once)

`sampan switch <name…> <profile>`: the last word is the profile, before it come session names or ids (several allowed). `--folder <path>` switches everything in that folder (subfolders included) instead, and then only the profile is given. `--from <profile>` switches only the ones currently on that profile and skips the rest; `--dry-run` only lists the plan; `--yes` skips the "start?" question when several are switched; `--no-launch` moves only stopped ones (transcript moved, registry row changed, nothing started; running ones are skipped). Skipped: busy or waiting sessions, Codex, retired, worktree, the pane sampan itself runs in, ones already on the target profile, ones not on `--from`. One table lists what happened to each session (switched, or skipped with the reason); conversation ids do not change. While `[mcp] confirm` is on, switching several at once (`--folder`, `--from`, or more than one name) is refused for an agent; `--dry-run` is not.
